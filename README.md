# Harness Notes

A personal notebook on agent planning, decisions and collaboration.

Read at [namanegi.github.io/harness-notes](https://namanegi.github.io/harness-notes/).

## Build

Requires Python 3.12 or later.

```sh
python -m pip install -r requirements.txt
python draw_diagrams.py
python build.py
python -m http.server 8080 --directory ..
```

Open `/harness-notes/`. The example assumes the checkout directory is named
`harness-notes`. After the one-time Pages setup below, GitHub Pages publishes
the site built from a published release's tag.

Articles are in `content/`; original sketch-style SVG diagrams are generated by
`draw_diagrams.py`. They are editable vectors, not Mermaid or raster images.
Selected Jev aggregates are in `assets/jev-evidence.json`.
See [sources and notices](SOURCES.md) for data provenance and publication scope.

The Jev series has three paired articles: capability and choice weights,
matched Jev/Luna decisions, and complete workflows. The existing `/projects/jev/`
route remains the workflow article. The homepage cards are native links.
The separate `/projects/jev-rerank/` article reports the October 2026 RAG
reranking experiment, with its own aggregate file and bilingual measured plots.
The theme defaults to dark and saves an explicit light/dark choice locally;
with JavaScript disabled the site remains readable in dark mode.

Licensed under Apache-2.0. This site is an editorial companion to the linked
studies. Selected synthetic case excerpts are published, not benchmark records
or complete private run transcripts.

## Publish a release

`.github/workflows/deploy-pages.yml` builds and deploys when a **published,
non-prerelease GitHub Release** has a tag starting with `v`. Merging into `main`,
pushing a tag alone, saving a draft, and publishing a prerelease do not deploy
through this workflow. It checks out the release tag, runs the Python build,
and uploads only the public HTML routes and assets from a staging directory.

### One-time repository setup

These settings are separate from the workflow and require repository admin
access. Until the Pages source is switched, the existing branch-based
deployment will still publish changes pushed to `main`.

1. **Before merging this workflow**, open Settings > Pages and change Build
   and deployment > Source from **Deploy from a branch** to **GitHub Actions**.
   This stops automatic publication from `main`.
2. In Settings > Environments > `github-pages` > Deployment branches and tags,
   add a **Tag** rule for `v*`. The existing `main` and `gh-pages` branch rules
   do not authorize tag deployments. Keep other environment protections.
3. Merge the workflow into `main`, then publish a release from a commit that
   includes it. The existing live site is replaced when deployment succeeds.

The equivalent setup commands for the current repository are:

```sh
gh api --method PUT repos/namanegi/harness-notes/pages -f build_type=workflow
gh api --method POST repos/namanegi/harness-notes/environments/github-pages/deployment-branch-policies -f name='v*' -f type=tag
```

Add the tag rule only if it is not already present. Inspect existing rules with
`gh api repos/namanegi/harness-notes/environments/github-pages/deployment-branch-policies`.

### Publish with GitHub CLI

From this repository, choose a new version and publish the latest remote
`main` (the command creates the tag if it does not already exist):

```sh
gh release create v2026.10.29 --target main --title "Site update 2026-10-29" --generate-notes
```

Use a new tag for each site update. For an exact reviewed commit, create and
push an annotated tag, then require that tag when publishing:

```sh
git tag -a v2026.10.29 <reviewed-commit-sha> -m "Site update 2026-10-29"
git push origin v2026.10.29
gh release create v2026.10.29 --verify-tag --generate-notes
```

These are alternative ways to publish the same version. The workflow deploys
the tag's content even if `main` moves afterward. A tag must include the
deployment workflow. To prepare release notes first, add `--draft` to the
create command and publish later with `gh release edit v2026.10.29 --draft=false`.
Avoid `--prerelease` for a production publication; prereleases are skipped.

Check deployment progress with:

```sh
gh run list --workflow deploy-pages.yml --limit 5
gh run watch <run-id> --exit-status
```

## Case previews

Reviewed bilingual examples live in `assets/jev-cases.json`. Add
`<!-- case:case-id -->` beside an article result to insert a preview link;
`<!-- case-library -->` renders all examples in the appendix. `case_previews.py`
renders both from the same records and rejects unknown IDs. The build does not
need access to the private experiment repository.

`assets/cases.js` enhances the normal appendix links with one native dialog per
article. Escape and Close return focus to the original link; modified clicks
and browsers without JavaScript keep normal link behavior. `assets/cases.css`
uses the shared theme variables. Input summaries are editorial, while selected
input/output fields and tool traces preserve recorded values. Original and
amended batches must keep separate case IDs and source-record references.

## Paired writing

English articles live in `content/`; their Chinese counterparts live in
`content/zh/`. Every publication and substantive correction updates both
versions in the same commit. Match the research question, method, claims,
numbers and caveats; natural phrasing can differ. Update both figure languages
in `draw_diagrams.py` when a diagram changes.

The build requires a counterpart for each page. English uses the root routes;
Chinese uses `/zh/`. The top-right language links stay on the corresponding
article. Shared numeric evidence remains in one aggregate file.
