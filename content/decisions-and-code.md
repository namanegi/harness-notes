# 把判断交给谁：模型、代码与决策的时机

namanegi · 2026-09-21 · Harness Engineering

一个 agent 收到“给订单预留库存”的请求，似乎只需不断问模型下一步做什么。但订单读出 SKU 和数量后，复制这两个字段不需要推理；主仓为零时，下一步去查备仓却需要根据新观察改变行动；最后是否已经完成，则应由库存状态而不是模型的自我报告判定。这三件事若都塞进同一个提示，系统可以运行，却很难知道成功来自哪里，失败又该修哪里。

我把 harness 看作一条**分配判断责任的边界**。代码负责有明确来源和可检查规则的变换：复制订单字段、匹配精确 ID、计算布尔条件、确认工具前置条件。模型负责那些规则仍不足以唯一决定、但候选和可见证据已经清楚的选择。开放式查询或说明文字交给生成模型，同时保留它所需的工具契约和观察。执行器最后独立核验状态，并把无匹配、调用预算耗尽、参数缺失分别记成不同终态。这不是“代码比模型聪明”的口号，而是让每个错误有可定位的责任层。

这条边界在一个小型 [Jev harness pilot](@/projects/jev/) 中变得具体。受约束的短动作路由容易做对，结构化枚举也便于拦截非法输出；但把完整复杂布尔表达式放进同样小的选项表，正确率就不再稳固。候选只有五项，不代表判断只需五选一的难度。英文逐字符探针也说明，已知目标词并不保证模型每次都能找准下一字符。[单体边界报告](@/projects/jev/)和[字符诊断](@/projects/jev/)把这些失败与短路由的成功分开记录。它们都是 pilot，不是对所有任务的能力排名。

因此，能由代码直接解决的问题不该被包装成语义选择。一个页面要求精确标题和祖先路径时，程序可检查字符串与 DOM 关系；模型选出近似按钮、再由同一模型复核，不会自动变成独立证据。在本轮[局部 DOM 回退实验](@/projects/jev/)中，给复核器完整祖先路径仍出现误点。树形搜索可以减少一次看到的候选，却也会丢掉全局参照；局部的 `none` 只表示当前叶组无匹配，不能偷换成整页无匹配。只有走完未试分支，系统才能作全局拒绝；预算先耗尽就应如实留下“未解决”。

另一个容易误会的边界是**低分转交**。Jev Choice 给出候选分布，但最高权重不是经校准的“这次行动成功概率”。在[实际条件转交试验](@/projects/jev/)中，固定门槛会省掉一部分生成模型请求，也会把某些本来正确的低分选择送去重做；后一次模型回答既可能纠错，也可能把正确答案改错。完整账单必须写成“筛选调用＋实际触发的后续调用＋验证与重试”，还要按任务族拆开看：简单题较易自动接受，难题若全数转交，筛选层只增加前置费用和串行等待。把两次独立生成的差异称为筛选器提高了后续模型能力，是因果关系上的越界。

“先做决定，还是边看边决定”在更长的工作流里同样关键。[Compile, Then Act? 的公开方法](https://github.com/namanegi/compile-then-act/blob/01c48be05391f6739fc59c88312a2c794cdf60b9/docs/methods.md)把 Online 定义为观察一批专家完成后再选下一批，Compiled 则在执行前生成并验证一次依赖图，运行中不改图；Single-agent 是另一个直接工具循环基线。这里的 Online 不是另一份 Jev 实验里的 Agents SDK ReAct，两个项目的控制器、任务和预算也不相同。Compiled 的优势假设是提前暴露可并行工作，减少等待调度；代价是后续新信息可能不在原图覆盖范围内。

CTA 的[冻结主报告](https://github.com/namanegi/compile-then-act/blob/01c48be05391f6739fc59c88312a2c794cdf60b9/results/formal-medium-v3/report.md)没有给出“预编译必然更快”的结论：主分析中 Compiled 的总体答案正确率点估计比 Online 低 2.5 个百分点，落在事先定义的五点质量边界内，但描述性区间不足以确立等效；FRAMES 上 Compiled 的运行完成只有 15/60。延迟方向在两个任务集之间改变，FRAMES 的 LLM 费用又有大量缺失用量。正确答案、正常结束和已知费用是三列不同的证据，不能让其中一列代替另两列。[简报](https://github.com/namanegi/compile-then-act/blob/01c48be05391f6739fc59c88312a2c794cdf60b9/results/formal-medium-v3/report-brief.md)里较整齐的四策略表属于**事后报告视图**：它用固定键的基础设施重试替换部分原记录，并把未触发救援的 Compiled 结果与触发后的真实路径拼成 Bounded 行。Bounded 是不完整 Compiled 运行之后才启动的选择性新执行，不是与前三者随机并列的第四策略。

这与 Jev pilot 的共同问题不是哪一个架构“赢”，而是**何时承诺一个判断**。预先编译依赖图，是在观察工具结果之前承诺未来工作的形状；每步 Choice，是在当前状态下承诺一个局部动作；低分转交，则先付筛选成本，再决定是否付生成成本。承诺越早，越可能省调度；承诺越晚，越能利用新证据，却需要更多调用。真正的比较单位应是从目标到终态的整条路径，而不是单次决策的平均延迟。

我现在会按一个顺序设计这类系统。先写出可见事实、工具契约和独立终态断言；把可复制、可计算、可精确匹配的部分交给代码。再圈出剩余的语义分叉，明确候选、拒选出口和模型能看到什么。最后冻结同题的完整系统对照，分别报告最终质量、完成、自动覆盖、调用数、延迟与费用覆盖率；看到结果后的修订另列。这个顺序会让“模型做得更少”成为可检验的工程选择，也会让它确实该发挥作用的地方有清楚的输入和边界。
